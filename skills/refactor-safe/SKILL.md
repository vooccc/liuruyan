# 工作模式纪律 · 重构安全档位

重构最容易翻车的不是技术，是**节奏**。下面是几条防翻车的护栏。

## 心法

**重构 = 在不改变外部行为的前提下，改善内部结构。**

如果改完行为变了——那不叫重构，叫**重写**。
重写要单独立项、明确告知用户、走另一套验证流程。

## 1. 行为不变是绝对底线

- **重构前必须有测试覆盖**——没有测试就别重构，先补测试
- **重构后所有现有测试必须通过**——挂一个都说明行为变了，必须停下来想清楚是 bug 还是有意改动
- **契约测试是命根子**：模块边界的契约测试绝对不能改，改了就不是重构了

## 2. 小步前进

- **每次提交都能独立通过测试**——不允许"重构进行中所以测试挂着"
- **每次只改一个维度**：
  - 抽函数 vs 改命名 vs 拆模块——一次只做一件，不混着搞
  - 这一步不抽函数，下一步再抽
- **每天至少能停在一个绿色状态**：万一被打断，代码不能是半瘫痪的

## 3. 测试金字塔不可跳

重构前盘点：

| 层级 | 应该有 | 没有的话 |
|---|---|---|
| **契约测试** | 模块对外接口的输入输出对照 | **先补再重构**，没契约重构无安全网 |
| **单元测试** | 核心算法/纯函数的边界用例 | 重构期间补，但优先级低于契约 |
| **集成测试** | 跨模块协作链路 | 锦上添花，可以重构后补 |

> 没有契约测试就硬重构 = 在没有麻醉的情况下做手术。**会出事**。

## 4. 可分阶段，可暂停

- **大重构必须能切片**：能拆成 N 个独立小重构，每个都可独立部署
- **每个切片都向后兼容**：旧调用方不改也能用，给迁移留窗口期
- **遇到不确定的，停下来**：宁可阶段性收尾让代码进半成品的临时状态躺一周，
  也不要硬冲一个连自己都没把握的大改

## 5. 命名 / 结构 / 算法分层重构

按风险从低到高：

1. **改命名**（最安全）：变量、函数名、文件名——IDE rename 工具一遍过
2. **抽函数 / 内联函数**：行为完全不变，只是切分粒度
3. **挪位置**：跨文件移动函数/类，调用方更新引用
4. **改结构**：拆类、合并类、改继承——这一步开始有真正的风险
5. **改算法**：实现方式变了，但接口不变——必须有强测试覆盖
6. **改接口**（最危险）：调用方都得跟着改——这其实已经不是重构，是 API 演进

**先把低风险的全做完再考虑高风险的**，不要跳级。

## 6. 沟通与文档

- **重构前写明动机**：为什么改？解决什么问题？预期收益？
- **大重构发起人有责任写迁移指南**：让别的协作者知道"我的代码该怎么跟着调整"
- **遗留陷阱要留注释**：删除某段代码时如果它解决过历史 bug，
  在新代码处留 `# 历史背景：xxx 解 xxx 短路` 类型的设计陷阱备忘录

## 7. 不允许的事

- ❌ "顺便" 重构：写新功能时别顺手把旁边的旧代码也改了——那不叫顺便，叫埋雷
- ❌ "一次性大改" ：500+ 行的 PR 没人能 review，等于无 review 合入
- ❌ 删测试让重构通过：测试挂了说明行为变了，停下想清楚，不要改测试

---

> **底线**：重构是"投资"——花时间换未来的可维护性。如果当前没有"未来需要维护"的需求，
> 那就不要重构。优先级永远是**功能 > 修 bug > 重构**。
